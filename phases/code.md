# Phase 4 — Write the code

Goal: implement the approved `$W/plan.md`, step by step, in the repo's conventions. Nothing more.

## Conventions
The repo's conventions are the law: its rules in `AGENTS.md`/`CLAUDE.md` (usually already in
context) and the docs they reference, plus `$CTX` § Code conventions / Core rules (imports, naming, where hooks,
pure logic and tests go, data-layer and codegen flow, theme, logging). On top of them, these defaults
apply unless `$CTX` § People & process says otherwise:
- **Match the design exactly**: size, weight, spacing, icon variant (outline vs solid, stroke),
  copy and case. Nothing the design lacks; no extra states, options or screens.
- **Small units**: a component past ~250 lines splits into components + a hook + pure utils. Clear
  names; shared things get generic names.
- **Logic out of components**: every non-trivial decision (sorting, filtering, formatting,
  eligibility, state transitions) goes in a pure function — it is what the Test phase unit-tests.
- **Comments**: none that explain what the code does; a one-line *why* only where the code can't show it.
- **Formatting**: run the repo's formatter on changed files (`$CTX` § Commands); a re-indent the
  formatter forces is fine — mention "hide whitespace" in the PR.
- **Where the change lives** follows the repo's stack and architecture: UI changes in the app's
  screens/components; backend changes in the layer the repo's conventions name (resolvers, handlers,
  services, migrations — reversible), with the contract (schema/API types) regenerated by its
  command. A change other repos or clients depend on (API shape, events) → say so in the plan.
- **Testable and accessible UI**: new interactive elements get an accessibility label/role and, where
  the repo uses them, a test id — the Test phase selects by them and the review checks them.
- New dependencies only when the plan approved them; native ones need a native rebuild (and, on iOS,
  a pod install — revert incidental project-file churn it causes, per `$CTX` § Git & PR).

## How to work
1. Re-read the files the plan touches; reuse what Phase 1/2 found (components, tokens, icons, hooks).
   Work through `plan.md`'s step checklist in order and tick each `[x]` when it is implemented.
2. The gate baseline (typecheck error total included) was taken in Preflight step 7 and is in
   `state.md`; only take it now if it's missing (resume of an older run), before the first edit.
3. Implement plan steps in order. After each, the touched files must typecheck (only your errors
   count; the total must stay at the baseline).
4. A step that turns out different from the plan in a way the user would notice → stop and ask
   (AskUserQuestion: planned vs actual vs impact). File-layout differences that don't change
   behaviour are not deviations.
5. Temporary code to force a state for testing is marked `// TEMPTEST <TICKET>` and never survives
   to Ship.

Done when every plan step is implemented and typechecks. Next: `phases/test.md`.
